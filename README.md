# Rivo

Mobile-first Progressive Web App (PWA) zur schnellen Erfassung von Serviceberichten für Serviceeinsätze im Elektrohandwerk. Läuft im Browser (iPhone Safari, Android Chrome, Desktop) und lässt sich wie eine native App auf dem Homescreen installieren – ganz ohne App Store.

> Hinweis: Die App heißt "Rivo" (Name + Logo, siehe Abschnitt "Design"). Repository-Name und die daraus abgeleitete GitHub-Pages-URL bleiben technisch bei `E-Servicebericht-`, um bestehende Links/Deploy-Konfiguration nicht zu brechen.

## Funktionen (MVP)

- **Projektnummer** je Servicebericht (Pflichtfeld), dazu optional Kurzbeschreibung, Kunde, Ansprechpartner beim Kunden, Techniker und Status (offen/abgeschlossen). Die Kurzbeschreibung wird zusätzlich zur Projektnummer auch auf der Berichts-Karte in der Übersicht angezeigt – man erkennt so auf einen Blick, um welches Projekt es sich handelt, ohne dass die Projektnummer allein aussagekräftig sein muss
- **Warnung vor Duplikaten beim manuellen Neuanlegen**: Wird über "+ Neuer Bericht" eine Projektnummer eingegeben, zu der bereits ein offener (nicht gesperrter) Bericht existiert, fragt die App beim Verlassen des Projektnummer-Feldes nach, bevor tatsächlich ein neuer (doppelter) Bericht angelegt wird – inkl. Projektnummer, Kurzbeschreibung und Kunde des bestehenden Berichts zur Wiedererkennung. Bestätigt man, wechselt man direkt in den bestehenden Bericht (ein evtl. durch die Autosave bereits im Hintergrund angelegter, noch leerer eigener Entwurf wird dabei automatisch aufgeräumt statt als Karteileiche liegen zu bleiben); bricht man ab, wird stattdessen bewusst ein neuer Bericht angelegt – dabei werden Kurzbeschreibung, Kunde und Ansprechpartner automatisch aus dem bestehenden Bericht vorausgefüllt (spart erneutes Eintippen bei einem weiteren Einsatz am selben Projekt), bleiben aber jederzeit frei änderbar. Ergänzt die bereits bestehende automatische Wiederverwendung beim "Direkt einchecken"-Schnellzugriff (dort ohne Rückfrage, siehe unten) um denselben Schutz für den bewussten manuellen Anlage-Weg
- **Tagesstempeluhr mit Leerlaufzeit-Tracking**: Oben in der Berichtsliste wird zunächst der ganze Arbeitstag ein-/ausgestempelt ("Tag einstempeln"/"Tag ausstempeln"), unabhängig von einem konkreten Projekt. Solange der Tag läuft, aber gerade in keinem Bericht eingecheckt ist, läuft die Zeit automatisch auf ein separates Konto **"Leerlaufzeit"** (Fahrten, Warten, Rüstzeiten, allgemeine Tätigkeiten). Der Wechsel zwischen Leerlaufzeit und einem Projekt (bzw. zwischen zwei Projekten) läuft über das gewohnte Ein-/Auschecken im jeweiligen Bericht (`TimeClock`) oder den "Direkt einchecken"-Schnellzugriff; es kann global immer nur ein Abschnitt gleichzeitig laufen (beim Wechsel zwischen zwei unterschiedlichen Projekten wird zur Sicherheit nachgefragt, beim Wechsel Leerlaufzeit↔Projekt nicht, da das der normale Ablauf ist). Solange der Tag läuft, zeigt eine "Heute bisher"-Kachel live die bereits angefallene Gesamt-/Projekt-/Leerlaufzeit (aktualisiert sich alle 30s, inkl. des gerade laufenden Abschnitts); nach dem Ausstempeln macht eine Tagesabschluss-Karte daraus den finalen Tages-Stand. Wird am selben Kalendertag mehrfach aus- und wieder eingestempelt, zählt die Tagesbilanz alle Zyklen dieses Tages zusammen – sie setzt sich erst am nächsten Kalendertag wieder auf 0 zurück. Begriffe sind bewusst getrennt: **ein-/ausstempeln** startet/beendet den Arbeitstag, **ein-/auschecken** wechselt in ein/aus einem Projekt
- **Pausen beim Tagesausstempeln**: Während einer Pause bleibt man laut Anleitung eingestempelt (Projekt oder Leerlaufzeit läuft einfach weiter) statt extra auszuchecken - beim Tippen auf "Tag ausstempeln" öffnet sich zuerst ein Pausen-Panel ("Pause gemacht heute?"), in dem sich beliebig viele Pausenfenster (Von/Bis) nachtragen lassen, bevor tatsächlich ausgecheckt wird. Für jede Pause wird die betroffene Zeit aus den überschneidenden Projekt-/Leerlaufzeit-Einträgen herausgeschnitten (dieselbe Kürzen-/Splitten-Logik wie bei der Überschneidungsprüfung, s.u.) - die Pausenzeit zählt weder als Projektzeit noch als Leerlaufzeit und wird nirgends bezahlt. Die Tagesabschluss-Karte zeigt zusätzlich "davon X Std. Pause abgezogen"; die einzelnen Pausenfenster eines Tages lassen sich in der Auswertung (Tag-Ansicht) einsehen und bei Bedarf wieder löschen - dabei wird die zuvor herausgeschnittene Zeit automatisch dem jeweiligen Projekt bzw. der Leerlaufzeit wieder gutgeschrieben (bei einem komplett innerhalb der Pause liegenden Eintrag wird dieser neu angelegt, bei einem gesplitteten Eintrag werden beide Teile wieder zu einem zusammengeführt) - eine zwischenzeitlich manuell veränderte oder gelöschte Nachbarzeit wird dabei übersprungen, statt die ganze Wiederherstellung abzubrechen. Eine vergessene oder nachträglich bekannte Pause lässt sich zusätzlich **manuell nachtragen**, unabhängig vom Tagesausstempeln: Im Zeitverlauf der Auswertung (Tag-Ansicht) steht ein "+ Pause hinzufügen"-Button, der dasselbe Von/Bis-Formular öffnet und dieselbe Kürzen-/Gutschrift-Logik nutzt - so lässt sich eine Pause auch für einen beliebigen, auch zurückliegenden Tag eintragen, ganz ohne dafür extra ein- und wieder auszustempeln. Mit exakten Von/Bis-Zeiten bewusst nur an dieser einen Stelle (Auswertung Tag-Ansicht) umgesetzt: Pausen sind ein Tages-, kein Projekt-Konzept (ein Tag kann mehrere Projekte umfassen, die Kürzen-Logik arbeitet ohnehin schon über den ganzen Tag statt über einen einzelnen Zeiteintrag), die Tag-Ansicht ist bereits die etablierte Stelle zum Ansehen/Löschen von Pausen, und das Kalender-Tagespanel verlinkt für tiefere Bearbeitung ohnehin auf genau diese Tag-Ansicht. Im Zeiten-Tab eines Projekts gibt es zusätzlich eine vereinfachte Variante ohne exakte Uhrzeiten (nur eine Dauer, automatisch mittig platziert, s.u.) – für den häufigen Fall "Pause direkt beim Nachtragen der Tageszeit mit abziehen", ohne den Umweg über die Auswertung
- **Leerlaufzeit manuell nachtragen und bearbeiten** (Auswertung → Tag-Ansicht, Teil des Zeitverlaufs s.u.): Wurde vergessen, ein- oder auszustempeln, fehlt für den betroffenen Zeitraum jede Erfassung. Ein "+ Leerlaufzeit hinzufügen"-Button öffnet dasselbe Von/Bis-Formular wie bei den Pausen und legt für einen beliebigen, auch zurückliegenden Tag einen neuen Leerlaufzeit-Eintrag an – eine dabei versehentlich überlappte Projekt-/Leerlaufzeit wird vorher automatisch herausgeschnitten (dieselbe Logik wie beim manuellen Pausen-Nachtragen), damit nichts doppelt gezählt wird. Der neue Eintrag verhält sich danach wie jede andere Leerlaufzeit und lässt sich über "Leerlaufzeiten zuordnen" (s.u.) einem Projekt zuweisen oder bleibt einfach Leerlaufzeit. **Ein Tap auf einen bestehenden Leerlaufzeit-Eintrag im Zeitverlauf** öffnet dasselbe Formular im Bearbeiten-Modus, vorausgefüllt mit den bisherigen Zeiten – z.B. um eine falsch eingetragene Uhrzeit zu korrigieren. Wird der Zeitraum dabei verkleinert oder verschoben, bleibt die dadurch freiwerdende Zeit als eigener Leerlaufzeit-Eintrag erhalten statt spurlos zu verschwinden (dieselbe Nicht-destruktiv-Logik wie beim Verkürzen eines Zeiteintrags im Zeiten-Tab, s.o.). Ein eigenes ↘-Icon direkt daneben öffnet stattdessen das **"Projekt zuordnen"-Panel**: erst ein (nicht gesperrter) Bericht per Suche auswählen, danach entweder die **komplette** Zeit zuordnen oder ein **Zeitfenster** daraus wählen (Von/Bis, standardmäßig auf den bisherigen Zeitraum vorausgefüllt) – bei einer Teil-Zuordnung wird der Leerlaufzeit-Eintrag auf genau dieses Fenster verkleinert und dem Bericht zugeordnet, die verbleibende Zeit davor bzw. danach bleibt als eigene Leerlaufzeit erhalten (bis zu zwei neue Einträge, je nachdem ob das Fenster am Rand oder mitten im bisherigen Zeitraum liegt) – dieselbe Zuordnung wie beim separaten Screen "Leerlaufzeiten zuordnen" (s.u.), nur direkt aus dem Zeitverlauf heraus und mit der zusätzlichen Möglichkeit, nur einen Ausschnitt statt der ganzen Zeitspanne zuzuordnen
- **Automatisches Ausstempeln bei Überschreitung der Höchstarbeitszeit**: Die verstrichene Zeit seit dem Einstempeln wird beim Öffnen der App und danach alle 30 Sekunden geprüft (solange sie geöffnet bleibt) - überschreitet sie 10 Std. 45 Min. (Höchstarbeitszeit 10 Std. nach §3 ArbZG PLUS die dabei gesetzlich vorgeschriebene Pflichtpause von 45 Min. nach §4 ArbZG - 30 Min. nach mehr als 6 Std., insgesamt 45 Min. nach mehr als 9 Std.), wird automatisch ausgestempelt, gekappt auf Einstempelzeit + 10 Std. 45 Min. (bewusst nicht auf den tatsächlichen Erkennungszeitpunkt, der je nach nächstem App-Start Stunden oder Tage später liegen könnte). Die Pflichtpause zählt bewusst mit in die Grenze hinein, nicht nur die reine Arbeitszeit: wer laut Anleitung während der Pause eingestempelt bleibt und sie erst beim Ausstempeln nachträgt, ist bei einem vollen legalen 10-Std.-Arbeitstag inkl. Pause 10 Std. 45 Min. am Stück eingestempelt - das ist noch kein Zeichen für ein vergessenes Ausstempeln. Ein Hinweis-Banner macht darauf aufmerksam ("Automatisch ausgestempelt") mit dem Hinweis, dass ggf. vergessen wurde, manuell auszustempeln, und die Zeiten (und ggf. Pausen) für diesen Tag in der Auswertung geprüft/nachgetragen werden sollten - inkl. Direktlink dorthin. Erkennt auch ein über mehrere Kalendertage vergessenes Auschecken (echte Datums-Differenz, nicht nur Uhrzeit-Arithmetik). Unabhängig davon werden einzelne Zeiteinträge, deren Dauer die reine Höchstarbeitszeit (10 Std., ohne Pausenzuschlag - ein einzelner Projekt-/Leerlaufzeit-Abschnitt ist ja bereits um evtl. erfasste Pausen bereinigt) überschreitet, überall wo sie angezeigt werden (Zeiten-Tab eines Berichts, Leerlaufzeiten-Liste, Projekt-Aufschlüsselung in der Auswertung) farblich hervorgehoben (rötlicher Hintergrund + Warnsymbol) als reiner Hinweis zur Prüfung - ohne die Zeiten selbst zu verändern
- **Eingecheckter Bericht angepinnt**: In der Berichtsliste steht der Bericht, in den gerade eingecheckt ist, immer ganz oben (unabhängig von der sonstigen Sortierung nach letzter Änderung) und ist farblich hervorgehoben (Rahmen/Hintergrund + "● Eingecheckt"-Badge) – auf einen Blick erkennbar, woran man gerade arbeitet
- **Leerlaufzeiten nachträglich zuordnen** (Menü → Leerlaufzeiten zuordnen): Alle abgeschlossenen, noch keinem Projekt zugeordneten Leerlaufzeit-Abschnitte lassen sich hier im Nachhinein einem (nicht gesperrten) Bericht zuweisen – was nicht zugeordnet wird, bleibt dauerhaft Leerlaufzeit
- **Manuelles Verkürzen eines Zeiteintrags erzeugt Leerlaufzeit statt Datenverlust**: Wird ein bestehender Zeiteintrag im Zeiten-Tab eines Berichts nachträglich verkleinert oder verschoben – z.B. weil im Nachhinein auffällt, dass ein Teil der Zeit tatsächlich für ein anderes Projekt draufging –, verschwindet die dadurch freiwerdende Zeit nicht einfach spurlos: Für die weggekürzte Zeitspanne wird automatisch ein eigener Leerlaufzeit-Eintrag angelegt (bei einer Verkürzung an beiden Enden entsprechend zwei), der sich anschließend wie jede andere Leerlaufzeit über "Leerlaufzeiten zuordnen" (s.o.) einem Projekt zuweisen lässt oder einfach Leerlaufzeit bleibt. Greift nur, wenn sowohl der bisherige als auch der neue Zeitraum vollständig sind (Start und Ende) und sich das Datum nicht ändert – ein noch offener Eintrag, der erstmals eine Endzeit bekommt, oder ein auf einen anderen Tag verschobener Eintrag wird weiterhin einfach normal aktualisiert, ohne Leerlaufzeit anzulegen (dafür gibt es keine sinnvoll vergleichbare "alte" Zeitspanne)
- **Auswertung** (Menü → Auswertung, vormals "Statistik" – umbenannt, da die Kalender-Ansicht mit dazugekommen ist): Tages-/Monats-/Jahres-Auswertung von produktiver Zeit (einem Bericht zugeordnet) vs. Leerlaufzeit, jeweils mit Vor-/Zurück-Navigation zum gewünschten Zeitraum, Gesamt-/Produktiv-/Leerlaufzeit-Kachel samt Prozent-Balken sowie einer Tages- bzw. Monats-Aufschlüsselung zum Reintippen in einen einzelnen Tag/Monat. Basiert auf allen erfassten Zeiteinträgen (auch manuell im Zeiten-Tab nachgetragenen, nicht nur über die Tagesstempeluhr erfassten). Die Tagesansicht zeigt zusätzlich einen **chronologischen Zeitverlauf**: ALLE Projekt-, Leerlaufzeit- und Pausen-Abschnitte dieses Tages in einer einzigen, nach Startzeit sortierten Liste (statt nach Kategorie gruppiert) – so lässt sich auf einen Blick nachvollziehen, was wann passiert ist ("erst Leerlaufzeit, dann Projekt X, dann Pause, dann wieder Leerlaufzeit"). Jeder Abschnitt ist farblich markiert (grüner Rahmen für Projektzeit, oranger für Leerlaufzeit, violetter für Pause) und zeigt Uhrzeit, Art/Projekt sowie Dauer; ein Tap auf einen Projekt-Abschnitt springt direkt zum jeweiligen Bericht, ein Tap auf einen Leerlaufzeit-Abschnitt öffnet ihn zum Bearbeiten (s.o.). Das Kalender-Tagespanel zeigt für denselben Tag weiterhin die ältere, nach Projekt gruppierte Aufschlüsselung mit Ausklapp-Pfeil pro Projekt-Zeile (Von–Bis Uhrzeit je Abschnitt, standardmäßig eingeklappt) – dort reicht der kompaktere Überblick, während die Tag-Ansicht selbst auf die vollständige Chronologie ausgelegt ist. In der Monatsansicht steht zusätzlich eine **Soll-/Ist-/Differenz-Kachel**: Das Soll ergibt sich aus allen Werktagen (Mo–Fr) des Monats ohne gesetzlichen Feiertag, mal der konfigurierten Sollstunden-pro-Woche ÷ 5 (Annahme 5-Tage-Woche) – und bleibt **fix**, unabhängig von Abwesenheiten. **Urlaub/Krank werden stattdessen als Ist-Zeit angerechnet** (ein Urlaubs-/Kranktag zählt mit den Sollstunden pro Tag zur Ist-Zeit, sofern er ohnehin ein Werktag gewesen wäre): so zeigt die Kachel auf einen Blick, wie viel vom festen Soll bereits durch Arbeit UND Urlaub/Krank abgedeckt ist und wie viel noch offen ist (mit Hinweiszeile "davon X Urlaubs-/Kranktage angerechnet"). **Zeitausgleich wird bewusst NICHT angerechnet**: ein ZA-Tag baut bereits an anderer Stelle erarbeitete Überstunden ab, indem an diesem Tag einfach weniger gestempelt wird – die niedrigere tatsächliche Ist-Zeit spiegelt das ganz von selbst in der Differenz wider (die App führt bewusst kein monatsübergreifendes Zeitkonto/Überstunden-Saldo, eine zusätzliche Gutschrift würde den Effekt doppelt zählen)
- **Kalender-Ansicht** (Auswertung → Kalender): Monats- oder Wochenraster wie in einem klassischen Kalender, jeder Tag farblich eingefärbt nach Status – Feiertag, Urlaub, Krank, Zeitausgleich, bereits gebuchter Werktag, noch offener (unbebuchter) Werktag, Wochenende – samt Legende. Die Priorität bei mehreren zutreffenden Status ist: Abwesenheit > Feiertag > gebuchte Zeit > Wochenende > offen (eine bewusst eingetragene Abwesenheit bleibt so z.B. auch dann sichtbar, wenn sie zufällig auf einen Feiertag oder ein Wochenende fällt). Ein Tap auf einen Tag verlässt den Kalender-Tab **nicht** – stattdessen klappt direkt darunter ein Infopanel für diesen Tag auf (erneutes Antippen desselben Tages klappt es wieder zu): bei bereits erfassten Zeiten die gewohnte Gesamt-/Produktiv-/Leerlaufzeit-Kachel samt Projekt-Aufschlüsselung (mit Link zur vollständigen Tagesansicht für tiefere Bearbeitung), bei einem noch offenen Werktag oder einem Tag mit bestehender Abwesenheit zusätzlich eine **Urlaub/Krank/Zeitausgleich-Schnellerfassung** direkt zum Antippen – ganz ohne Umweg über den Abwesenheiten-Screen. Bei bereits gebuchter Zeit, Feiertagen oder Wochenenden gibt's bewusst keine Schnellerfassung, um echte Daten nicht versehentlich zu überlagern
- **Abwesenheiten** (Menü → Abwesenheiten): Für einen beliebigen Zeitraum – auch rückwirkend oder in der Zukunft, unabhängig von der Tagesstempeluhr – lässt sich **Urlaub**, **Krank** oder **Zeitausgleich** eintragen, mit optionaler Notiz. Ein "Von"-/"Bis"-Datumsfeld deckt sowohl einen Einzeltag (Von = Bis, Standard) als auch einen mehrtägigen Zeitraum ab (z.B. eine ganze Urlaubswoche in einem Schritt); intern bleibt jeder Kalendertag weiterhin ein eigener Datensatz, Pro Tag ist immer nur ein Eintrag möglich (ein erneutes Speichern für denselben Tag überschreibt den vorherigen). Die Jahresübersicht mit Vor-/Zurück-Navigation zeigt alle Einträge des gewählten Jahres samt Zusammenfassung ("X Urlaub · Y Krank · Z Zeitausgleich"), jeder Eintrag lässt sich per Antippen bearbeiten oder löschen. Sind an einem der betroffenen Tage bereits Zeiten erfasst, wird vor dem Speichern einmal nachgefragt. Fließt direkt in die Soll-/Ist-Berechnung und die Kalender-Ansicht der Auswertung ein (s.o.)
- **Gesetzliche Feiertage** werden ohne externe API/Bibliothek berechnet (u.a. Gauß'sche Osterformel für die beweglichen Feiertage) – die neun bundesweiten Feiertage immer, dazu optional die landesspezifischen (Heilige Drei Könige, Fronleichnam, Mariä Himmelfahrt, Reformationstag, Allerheiligen), sobald in den Einstellungen ein Bundesland gewählt ist
- **Ein-/Auschecken pro Bericht**: Ein Tap startet einen laufenden Zeiteintrag (Startzeit = jetzt), ein weiterer Tap beendet ihn (Endzeit = jetzt, Dauer wird automatisch berechnet) und wechselt zurück auf Leerlaufzeit, falls der Tag noch läuft. Der entstandene Zeiteintrag lässt sich wie jeder andere im Zeiten-Tab manuell nachbearbeiten
- **Zeiten pro Tag** erfassen: Datum, Start-/Endzeit (Dauer wird automatisch berechnet – liegt die Endzeit vor der Startzeit, wird das als Zeitspanne über Mitternacht hinweg interpretiert, z.B. 19:05–12:16 → 17:11 Std., statt die Dauer zu verwerfen), optionale Notiz. Ein neuer Eintrag ("+ Tag hinzufügen") ist mit dem heutigen Datum sowie Start 08:00/Ende 17:00 vorbelegt – deckt den Normalfall (ein typischer Arbeitstag) ohne Eintippen ab, bleibt aber natürlich frei änderbar; beim Bearbeiten eines bestehenden Eintrags werden stattdessen dessen tatsächliche Werte angezeigt. Eine **"Pause abziehen"-Checkbox** direkt im selben Formular blendet ein Stunden-Feld ein (Default 0,5 Std., frei editierbar für längere Pausen) – ganz ohne exakte Pausen-Uhrzeiten eintippen zu müssen: Die Pause wird automatisch mittig in den eingegebenen Zeitraum gelegt (dieselbe Kürzen-/Splitten-Logik wie unten bei Überschneidungen) und taucht als eigener Pause-Eintrag in der Auswertung auf (s.u.). Beim Speichern wird berichtsübergreifend auf Überschneidungen mit anderen Zeiteinträgen am selben Tag geprüft (man kann ja nicht gleichzeitig an zwei Orten arbeiten) – bei einer Überschneidung fragt EIN Dialog nach, ob trotzdem gespeichert werden soll (das Kürzen der überschneidenden Zeit kündigt der Dialog dabei bereits an und passiert bei Bestätigung automatisch mit, statt als zweite, leicht übersehbare Rückfrage): je nachdem wo sich die Zeiten überlappen, wird der jeweils andere Eintrag entsprechend gekürzt oder – falls der Ausschnitt mittendrin liegt – in zwei Teile gesplittet, der übrige (nicht überschneidende) Zeitraum bleibt dabei erhalten
- **Verbautes Material**: Bezeichnung, Menge, Einheit, optionale Artikelnummer – mit Autovervollständigung aus einem mitgelieferten Standard-Materialstamm für Elektroinstallation (`src/lib/materialCatalog.ts`) sowie bereits im Bericht verwendeten Bezeichnungen
- **Material per Scan erfassen** ("📷 Scannen"-Button neben "+ Position hinzufügen") – zwei wählbare Erfassungsarten, per Tab-Umschalter im Scanner:
  - **QR-Code**: Öffnet die Kamera (per `jsQR`, dynamisch nachgeladen – lädt nicht mit, solange nicht gescannt wird) und liest laufend den QR-Code, den Lieferanten wie Sonepar auf jedes gelieferte Produkt kleben. Erkennt darin enthaltene GS1-Element-Strings (sowohl die menschenlesbare "(01)…(240)…"-Klammer-Schreibweise als auch den rohen, per FNC1/GS-Steuerzeichen getrennten Element-String) und übernimmt Artikelnummer und Stückzahl automatisch ins Formular – bei einem nicht erkannten Format greift ersatzweise eine Muster-Suche nach Stückzahl-Einheiten (Stk/Stück/pcs) und einer plausiblen Ziffernfolge. Die **Produktbeschreibung wird bewusst NICHT automatisch befüllt**: GS1-Codes transportieren grundsätzlich keinen Freitext, nur IDs/Mengen
  - **Etikett-Text**: Fotografiert stattdessen den gedruckten Text auf dem Etikett und liest ihn per Texterkennung (OCR, `tesseract.js`, deutsches Sprachmodell) aus – anders als der QR-Code steht dort häufig auch die **Produktbeschreibung** als lesbarer Text, zusätzlich zu Artikelnummer und Stückzahl, die per Zeilenmuster-Heuristik herausgesucht werden (`src/lib/utils/labelOcr.ts`). Alle drei Felder werden, sofern erkannt, automatisch ins Formular übernommen. Da Kamerafotos (Beleuchtung, Winkel, Schriftgröße) fehleranfälliger als ein exakt dekodierter Code sind, bleiben die Ergebnisse besonders wichtig zum Gegenprüfen – der komplette erkannte Rohtext wird dafür zusätzlich angezeigt
  - In beiden Modi bleiben alle übernommenen Werte wie gewohnt vor dem Speichern frei editierbar; ein Hinweis zeigt zusätzlich den rohen Scan-/Erkennungstext an. Läuft die Kamera nicht an (kein Zugriff erlaubt, kein Gerät) oder wurde ein QR-Code bereits mit einer anderen App gelesen, lässt sich der Rohtext stattdessen über "Code manuell eingeben" einfügen – derselbe Verarbeitungsweg wie beim Kamera-Scan
  - Die OCR-Engine (Worker-Skript, WASM-Kern, deutsche Trainingsdaten – zusammen mehrere MB) ist komplett selbst gehostet (kein CDN) und läuft dank Vite/Workbox-`runtimeCaching` beim ersten tatsächlichen Etikett-Text-Scan per HTTP nach, statt die Erstinstallation der App aufzublähen – ab dann per Service Worker dauerhaft zwischengespeichert und offlinefähig
- **Fotos** des Einsatzes über Kamera oder Fotobibliothek hochladen, mit Vollbild-Ansicht
- **Bericht sperren – mit oder ohne Unterschrift**: Ein Bericht lässt sich final abschließen und damit sperren (Kopfdaten, Notizen, Zeiten, Material und Fotos lassen sich danach nicht mehr ändern, eine laufende Stempeluhr wird automatisch beendet und wechselt dabei nahtlos auf Leerlaufzeit weiter – der Tagesstempel läuft also einfach weiter statt hängen zu bleiben –, der Status springt auf "Abgeschlossen") – auf zwei Wegen:
  - **Kunden-Unterschrift**: Im Tab "Unterschrift" unterzeichnet der Kunde vor Ort mit dem Finger oder der Maus auf einem Unterschriften-Pad (samt Name); das sperrt den Bericht automatisch mit
  - **Manuell durch den Monteur**: Über den Button "Ohne Unterschrift final abschließen", wenn keine Kundenunterschrift nötig oder möglich ist

  Sowohl in der Berichtsliste (Badge, plus Filter "Gesperrt" neben "Alle/Offen/Abgeschlossen") als auch im Bericht selbst wird "Unterschrieben" bzw. "Final abgeschlossen" als eigener, genauerer Status angezeigt statt nur "Abgeschlossen" – farblich und mit Icon unterscheidbar (siehe Abschnitt "Design"). Einziger Weg zurück zum Bearbeiten: die Sperre bewusst wieder aufheben (Button im Banner bzw. "Entfernen" im Unterschrift-Tab, jeweils mit Sicherheitsabfrage) – eine vorhandene Unterschrift geht dabei mit verloren und müsste neu eingeholt werden. Eine vorhandene Unterschrift erscheint im Word-Export als eigener Abschnitt am Ende des Dokuments
- **Export-Nachverfolgung**: Die Berichtsliste zeigt pro Bericht an, wann er zuletzt als Word-Dokument heruntergeladen/geteilt wurde ("Exportiert am …"), und bietet einen Filter "Nicht exportiert". Zusätzlich bekommt ein abgeschlossener, aber noch nicht exportierter Bericht direkt in der Liste einen eigenen dezenten "Nicht exportiert"-Hinweis, damit sich auf einen Blick erkennen lässt, welche fertigen Berichte noch eingereicht werden müssen
- **Export als Word-Dokument (.docx)**: kompletter Bericht (Kopfdaten inkl. Kurzbeschreibung/Ansprechpartner, Zeiten-Tabelle, Material-Tabelle, Notizen, Fotos, Kunden-Unterschrift) als editierbare Datei mit farblichem Layout (Theme-Akzentfarbe, Tabellen-Header-Shading, Zebra-Streifen) – läuft rein clientseitig (kein Server), mit direktem Teilen über das iOS-Share-Sheet (Mail/WhatsApp/AirDrop), wenn verfügbar
- **Sammelexport** (Menü → Serviceberichte sammelexportieren): exportiert alle noch nicht exportierten Berichte auf einmal statt einzeln. Erst wird der zu prüfende Zeitraum gewählt (gesamter Zeitraum oder ein bestimmter: heute, diese Woche, dieser Monat, individueller Zeitraum), dann zeigt die App die gefundene Anzahl mit Kurzvorschau (Projektnummern) an und fragt explizit nach Bestätigung, bevor tatsächlich exportiert wird. Bevorzugt – wie beim Einzel-Export – `navigator.share()` mit allen Dateien auf einmal (z.B. für AirDrop/Mail auf dem iPhone); ist das nicht verfügbar, werden alle Word-Dokumente stattdessen in ein einziges ZIP-Archiv gepackt und heruntergeladen, da mehrere einzelne Downloads hintereinander in iOS Safari unzuverlässig sind. Jeder erfolgreich exportierte Bericht wird automatisch als exportiert markiert; bricht man das Teilen-Sheet ab, bleibt nichts markiert
- **Backup & Wiederherstellung**: Der komplette Datenbestand (alle Berichte, Zeiten, Material, Fotos) lässt sich über das Menü als eine JSON-Datei sichern ("Sicherung exportieren") und auf einem anderen Gerät/nach Datenverlust wieder einspielen ("Sicherung wiederherstellen") – wichtig, da alle Daten sonst ausschließlich lokal auf einem Gerät liegen. Vor dem Import wird eine Zusammenfassung angezeigt und um Bestätigung gebeten; vorhandene Berichte mit gleicher ID werden dabei überschrieben
- **Menü statt Icon-Reihe**: Auswertung, Leerlaufzeiten zuordnen, Abwesenheiten, Einstellungen sowie Sicherung exportieren/wiederherstellen sind in der Berichtsliste über einen Menü-Button oben rechts erreichbar, der ein Popup-Menü mit Icon + Beschriftung je Punkt öffnet – statt vieler einzelner, nicht selbsterklärender Icons
- **Einstellungen** (Menü → Einstellungen): Techniker-Name (identisch zur Autofill-Logik bei neuen Berichten, s.u.), Sollstunden pro Woche sowie Bundesland – Grundlage für die Soll-/Ist-Berechnung in der Auswertung und die Feiertagsberücksichtigung. Ohne gewähltes Bundesland zählen nur die neun bundesweiten Feiertage, um keine falschen landesspezifischen Feiertage anzunehmen
- **Autosave** – kein Speichern-Button nötig, Eingaben werden automatisch gesichert
- **Offlinefähig** – alle Daten liegen lokal auf dem Gerät (IndexedDB), keine Internetverbindung nötig
- **Installierbar** – "Zum Home-Bildschirm hinzufügen" für App-artiges Verhalten auf iOS/Android
- **Direkt einchecken**: Button in der Tagesstempeluhr öffnet zuerst eine Auswahl der noch offenen Berichte zum direkten Weiterarbeiten; passt keiner, legt "+ Neuen Bericht anlegen" wie gehabt mit nur der Projektnummer sofort einen neuen Bericht an (startet bei Bedarf transparent den Tagesstempel mit) – Kopfdaten lassen sich danach in Ruhe nachtragen. Gibt es zu der eingegebenen Projektnummer bereits einen offenen Bericht, wird der wiederverwendet statt ein Duplikat anzulegen (kurzer Hinweis, wohin man eingecheckt wurde); gibt es dazu nur bereits abgeschlossene/gesperrte Berichte (z.B. erneuter Einsatz bei wiederkehrendem Kunden), wird ein neuer angelegt und die Besuchsnummer eingeblendet ("2. Bericht zu diesem Projekt") – dauerhaft sichtbar auch als Badge in der Kopfzeile des Berichts selbst ("2. von 3"). Dieser Badge ist antippbar und klappt eine Liste aller anderen Berichte zu derselben Projektnummer auf (jeweils mit Anlagedatum und Status, der gerade geöffnete Bericht ist markiert und nicht anwählbar) – ein Antippen eines der anderen Einträge springt direkt dorthin, ohne Umweg über Suche/Filter in der Berichtsliste. Der Badge (und damit die Sprung-Liste) erscheint automatisch immer dann, wenn manuell ("+ Neuer Bericht") oder automatisch mehrere Berichte zur selben Projektnummer angelegt wurden, unabhängig vom Direkt-einchecken-Flow
- **Techniker-Name wird gemerkt**: Der zuletzt eingetragene Techniker-Name wird lokal auf dem Gerät gemerkt und bei jedem neuen Bericht automatisch vorausgefüllt – erspart wiederholtes Eintippen
- **Kopfdaten einklappbar**: Ein bereits angelegter Bericht zeigt Projektnummer/Kunde zunächst nur als kompakte, antippbare Kopfzeile – mehr Platz für Zeiten/Material/Fotos auf kleinen Bildschirmen; ein Tap klappt die vollen Kopfdaten bei Bedarf wieder auf
- **Suche in der Berichtsliste**: Textsuche über Projektnummer und Kunde, zusätzlich zu den Status-Filtern

Aktuell bewusst außerhalb des Umfangs: PDF-Export, Login/Mehrbenutzer-Verwaltung, Cloud-Sync, ein automatischer Überstunden-/Zeitkonto-Saldo über mehrere Monate hinweg, halbe/anteilige Abwesenheitstage, sowie bei der Tagesstempeluhr (Phase 1+2 umgesetzt): Export der Statistik als Word/PDF, automatischer Pausenabzug nach §4 ArbZG und Fahrtzeiten-/km-Erfassung – geplant als spätere Ausbaustufen. Das Datenmodell ist aber so aufgebaut, dass sich das später ergänzen lässt, ohne die App umzubauen.

## Design

Die App wird schrittweise nach einem Moodboard überarbeitet. **Runde 1 (umgesetzt):**
- Neue Farbpalette als CSS-Variablen in `src/app.css` (Akzent `#2563EB`, Erfolg `#16A34A`, Text/Hintergrund-Töne), durchgängig angewendet (Buttons, FAB, Filter-Chips, PWA-Theme-Farbe, Word-Export-Akzentfarbe, App-Icon)
- [Inter](https://rsms.me/inter/) als Schriftart – selbst gehostet als Variable-Font-Datei (`src/assets/fonts/`, ~48 KB, deckt alle Schriftschnitte ab), bewusst **nicht** über Google Fonts CDN eingebunden, damit sie auch offline zuverlässig lädt (wird vom Service Worker mit vorgecacht)
- Globale Überschriften-Skala (h1/h2/h3) als Basis für neue Screens

**Runde 2 (umgesetzt):**
- Durchgängiges Icon-Set (`src/lib/components/Icon.svelte`) anstelle der bisherigen Emoji-Icons: eine kleine, feste Auswahl selbst gehosteter SVG-Icons im Stil von [Feather Icons](https://feathericons.com/) (MIT-Lizenz), direkt als Konstante eingebettet – wie schon die Schriftart bewusst **ohne** npm-Icon-Paket und **ohne** Laufzeit-Abhängigkeit von einem CDN, damit die App zu 100 % offlinefähig bleibt
- Feinschliff der Status-/Badge-Farbsemantik: "Unterschrieben" (vom Kunden signiert) und "Final abgeschlossen" (manuell ohne Unterschrift gesperrt) sehen jetzt farblich unterschiedlich aus (Blau vs. dunkles Anthrazit aus dem Moodboard-Ton `--color-ink`), obwohl beide den Bericht sperren – vorher teilten sie sich dieselbe Farbe. Abgeschlossene, aber noch nicht exportierte Berichte bekommen zusätzlich einen dezenten "Nicht exportiert"-Hinweis in der Übersicht als Erinnerung, den Bericht noch als Word-Dokument zu exportieren

**Runde 3 (umgesetzt) – Rebrand zu "Rivo":**
- Echtes Logo (`src/assets/logo.svg`, auch Quelle für `public/favicon.svg` sowie alle PWA-/Homescreen-Icons): stilisiertes "R"-Monogramm (weißer Stamm/Bogen, lime-grünes diagonales "Bein") auf dunklem, abgerundetem Badge – als flaches SVG nachgebaut nach der vom Kunden gelieferten Logo-Vorlage, nicht als eingebettetes Rasterbild, damit es in jeder Icon-Größe (Favicon bis 512px-Homescreen-Icon) scharf bleibt. Eigene maskable-Variante mit zusätzlichem Sicherheitsabstand für Android.
- App-Name durchgängig auf **"Rivo"** umgestellt (Seitentitel, PWA-Manifest `name`/`short_name`, "Zum Home-Bildschirm"-Titel, Berichtsliste-Header mit Logo + Wordmark, Sicherungsdatei-Name/-Fehlertext). Bewusst **nicht** angefasst: das interne Sicherungsdatei-Format-Tag (`e-servicebericht-backup-v2`, siehe `backupFile.ts`) und der IndexedDB-Datenbankname – eine Umbenennung dieser rein internen Kennungen hätte bereits vorhandene Sicherungen/lokale Daten ungültig gemacht bzw. verwaist, ohne jeden sichtbaren Nutzen.
- Die restliche Farbpalette (Primär-Blau aus Runde 1) und Typografie bleiben im Hell-Theme unverändert – nur Logo/Icon-Assets und der Marken-Akzent im Header (`--color-brand-accent`, ein abgedunkeltes Lime für Lesbarkeit auf hellem Grund) nutzten zu diesem Zeitpunkt schon den neuen Rivo-Ton.

**Runde 4 (umgesetzt) – vollständiges Dunkel-/Lime-Theme + Umschalter:**
- Komplettes zweites Farbschema in `src/app.css` (`:root[data-theme="dark"]`, überschreibt jeden Farb-Token): fast schwarzer Hintergrund, Lime-Grün (`#a3e635`) statt Blau als Primärfarbe, aufgehellte Status-/Badge-Farben (Erfolg/Gefahr/Offen/Unterschrieben/Final abgeschlossen) mit halbtransparenten statt pastellfarbenen Badge-Hintergründen, damit sie auf dunklem Grund noch als eigene Fläche erkennbar bleiben. Da ausnahmslos alle Farben in der App über diese CSS-Variablen laufen (keine hartkodierten Hex-/rgb-Werte in Komponenten-Styles), reicht das eine Token-Set, um wirklich jeden Screen umzufärben.
- Zwei bewusste Ausnahmen vom Theme: der Unterschrift-Bereich (`SignatureSection.svelte`, Zeichenfläche + Vorschau) bleibt immer hell mit dunkler Tinte – wie auf Papier unterschreiben, unabhängig vom Theme, und relevant für den späteren Word-Export; die Fotoansicht im Vollbild (`PhotoSection.svelte`) bleibt immer dunkel hinterlegt (unabhängig vom Theme, wie in den meisten Foto-Apps üblich).
- Umschalter im Menü ("Dunkles Design" / "Helles Design" mit Sonne-/Mond-Icon je nach aktuellem Zustand) sowie neues Modul `src/lib/theme.svelte.ts` (gleiches schlankes Muster wie `router.svelte.ts`: ein modul-weiter `$state`-Wert plus `setTheme()`/`toggleTheme()`). Die Wahl wird in `localStorage` gemerkt; ohne gespeicherte Wahl greift einmalig die Systemeinstellung (`prefers-color-scheme`). Ein kleines Inline-Script in `index.html` setzt das Theme-Attribut schon vor dem Laden des JS-Bundles, damit bei Dunkel-Systemeinstellung kein kurzer Hell-Flash beim Start auftritt.

## Tech-Stack

- [Vite](https://vitejs.dev/) + [Svelte 5](https://svelte.dev/) + TypeScript
- [`idb`](https://github.com/jakearchibald/idb) als schlanker IndexedDB-Wrapper (lokale Datenhaltung, kein Backend)
- [`docx`](https://github.com/dolanmiu/docx) für den clientseitigen Word-Export (per dynamischem Import nachgeladen, nicht im Hauptbundle)
- [`jszip`](https://github.com/Stuk/jszip) fürs ZIP-Archiv beim Sammelexport (ebenfalls dynamisch nachgeladen; war zuvor schon transitiv über `docx` vorhanden, jetzt als direkte Abhängigkeit)
- [`jsqr`](https://github.com/cozmo/jsQR) für den QR-Code-Scan beim Material-Erfassen (dynamisch nachgeladen, reines JS ohne WASM/native Abhängigkeiten – funktioniert deshalb auch auf iOS Safari ohne `BarcodeDetector`-API)
- [`tesseract.js`](https://github.com/naptha/tesseract.js) für die Etikett-Text-Erkennung (OCR) beim Material-Erfassen (dynamisch nachgeladen; Worker-Skript, WASM-Kern und deutsche Trainingsdaten liegen selbst gehostet unter `public/tesseract/`/`public/tessdata/` statt per CDN, passend zum Offline-First-Ansatz der App, und werden erst beim ersten tatsächlichen Scan per Workbox `runtimeCaching` nachgeladen/gecacht)
- [`vite-plugin-pwa`](https://vite-pwa-org.netlify.app/) für Manifest + Service Worker (Workbox)
- [Inter](https://rsms.me/inter/) (selbst gehostete Variable-Font) als Schriftart
- [Vitest](https://vitest.dev/) + [`fake-indexeddb`](https://github.com/dumbmatter/fakeIndexedDB) für die Tests der Datenzugriffsschicht

## Entwicklung

```bash
npm install
npm run dev        # Dev-Server unter http://localhost:5173
```

### Auf einem echten iPhone testen

iOS Safari verlangt für Service Worker/Kamera-Zugriff einen sicheren Kontext (HTTPS oder `localhost`). Für Tests im heimischen WLAN über die LAN-IP steht ein zweiter Dev-Befehl mit automatisch erzeugtem, vertrauenswürdigem Zertifikat (via `vite-plugin-mkcert`) bereit:

```bash
npm run dev:iphone
```

Die angezeigte `https://<LAN-IP>:5173`-Adresse dann auf dem iPhone im selben WLAN in Safari öffnen. Über **Teilen → Zum Home-Bildschirm hinzufügen** lässt sich die App wie eine native App installieren (App-Icon, Start ohne Safari-Oberfläche, Offline-Start).

> Hinweis: Beim allerersten Aufruf lädt `mkcert` einmalig einen Zertifikats-Helper aus dem Internet nach. Daher ist dieser Modus nicht Teil von `npm run dev`/`build`/`check`, damit diese Befehle nie von einem Netzwerkzugriff abhängen.

### Weitere Befehle

```bash
npm run build       # Produktions-Build nach dist/ (inkl. Service Worker/Manifest)
npm run preview      # Gebauten Build lokal ausliefern
npm run check         # Typ-/Svelte-Check (svelte-check)
npm test               # Unit-Tests einmalig ausführen (vitest run)
npm run test:watch  # Unit-Tests im Watch-Modus
```

## Projektstruktur

```
src/
  main.ts, App.svelte, app.css   # Einstiegspunkt, Root-Layout, globale Styles
  routes/
    ReportList.svelte             # Startseite: Liste aller Berichte
    ReportDetail.svelte           # Bericht anlegen/ansehen/bearbeiten
    Leerlaufzeiten.svelte          # Unzugeordnete Leerlaufzeit nachträglich einem Bericht zuordnen
    Statistik.svelte               # Tages-/Monats-/Jahres-Auswertung inkl. Soll-/Ist-Stunden
    Abwesenheiten.svelte           # Urlaub/Krank/Zeitausgleich erfassen + Jahresübersicht
    Einstellungen.svelte           # Techniker-Name, Sollstunden/Woche, Bundesland
  lib/
    db/                            # IndexedDB-Datenzugriffsschicht (Repository-Pattern)
      types.ts, client.ts, summary.ts, backup.ts, stats.ts
      reports.ts, timeEntries.ts, materialItems.ts, photos.ts, workDays.ts, absences.ts
    export/                        # Word-Export: getFullReport.ts (Daten aggregieren), docxExport.ts (Dokument bauen)
    backup/                         # backupFile.ts: Sicherungsdatei bauen/einlesen (Fotos base64-kodiert)
    components/                   # UI-Bausteine (Zeiten/Material/Fotos-Sektionen, PWA-Hinweise, …)
    utils/                          # Datum/Dauer-Formatierung, Debounce, Thumbnail-Erzeugung
      holidays.ts                    # Gesetzliche Feiertage (Gauß'sche Osterformel, bundeslandabhängig)
      targetHours.ts                 # Soll-Stunden pro Monat (Werktage abzüglich Feiertage/Urlaub/Krank)
      calendarDay.ts                  # Tages-Status (Urlaub/Krank/ZA/Feiertag/Gebucht/Wochenende/Offen) für die Kalender-Ansicht
    materialCatalog.ts               # Standard-Materialstamm für die Bezeichnung-Autovervollständigung
    settings.ts                      # localStorage-Einstellungen (Techniker-Name, Sollstunden/Woche, Bundesland)
    clockActions.ts                  # Orchestriert Tagesstempeluhr + Projekt-Ein-/Auschecken
    router.svelte.ts                # Minimaler Hash-Router (kein zusätzliches npm-Paket nötig)
  tests/                            # Vitest-Tests für Datenzugriffsschicht, Export, Backup und Utils
```

Die UI greift nie direkt auf `idb` zu, sondern ausschließlich über die Funktionen in `src/lib/db/*.ts`. Das hält die Komponenten einfach und erlaubt es später, die lokale Implementierung z.B. durch ein synchronisierendes Backend zu ersetzen, ohne den UI-Code anzufassen.

## Daten & Datenschutz

Alle Berichte, Zeiten, Materialpositionen und Fotos werden ausschließlich lokal im Browser-Speicher (IndexedDB) des jeweiligen Geräts abgelegt – es gibt (noch) keinen Server und keine Cloud-Synchronisation. Das bedeutet auch: Die Daten sind aktuell an das jeweilige Gerät/den jeweiligen Browser gebunden und nicht automatisch zwischen mehreren Geräten verfügbar.
